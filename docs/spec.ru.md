# Title Dedup: устройство

[English version](./spec.md)

## Цель

Когда в целевую ленту приходит новая статья, а в ленте-источнике того же правила уже есть статья с таким же нормализованным заголовком, целевая статья помечается прочитанной.

## Рамки

- Несколько правил, в каждом несколько лент-источников и несколько целевых лент
- По умолчанию одностороннее: источники влияют на цели, но не наоборот
- Лента может быть и источником, и целью. Если указать все разделы сайта с обеих сторон, первая копия каждой новости останется непрочитанной, а все последующие будут помечены прочитанными
- Точное совпадение после нормализации заголовка

## Не входит в задачи

- Сравнение по похожести текста
- Поиск дублей между языками
- Изменения ядра FreshRSS
- Поиск дублей на стороне клиента

## Как работает

### Новые статьи (хук `entry_before_insert`)

FreshRSS держит новые статьи в `_entrytmp` до конца обновления и только потом переносит их в `_entry`. Поэтому поиск идёт по обеим таблицам, и копии, пришедшие в одном обновлении, тоже сравниваются.

На первой новой статье запроса, которая относится к правилу, заголовки лент этого правила за период поиска загружаются один раз и дальше поддерживаются в памяти. Каждая новая статья обрабатывается в порядке прихода:

1. Если статья из целевой ленты, не прочитана и её заголовок уже известен из другой ленты-источника, это дубль: она помечается прочитанной.
2. Если статья из ленты-источника, не прочитана и сама не дубль, непрочитанные статьи целевых лент с тем же заголовком из других лент помечаются прочитанными: копия источника пришла позже них.
3. Заголовок запоминается как известный для своей ленты. Непрочитанная целевая статья, которая не оказалась дублем, запоминается на случай, если её источник придёт позже.

Прочитанная статья служит только образцом и никогда не гасит другие. Иначе копия, погашенная предыдущим проходом, могла бы погасить уцелевший оригинал.

Обновлённые версии уже известных статей не проверяются.

### Разовая проверка (хук `freshrss_user_maintenance`)

После сохранения правил ближайший запуск обслуживания прогоняет уже накопленные статьи за период поиска в порядке прихода (по ID статьи) по той же логике. Последующие запуски ничего не делают, поэтому статья, которую пользователь вернул в непрочитанные, такой и останется. Повторное сохранение правил повторяет проверку, и уже обработанные статьи она не меняет.

## Конфигурация

Хранится у каждого пользователя в виде JSON в пользовательской конфигурации расширения. Поля правила:

- `name`
- `enabled`
- `source_feed_ids`, `source_feed_names`
- `target_feed_ids`, `target_feed_names`
- `lookback_days`
- `normalize_whitespace`
- `normalize_case`
- `strip_punctuation`

Версия 0.1 хранила правила в системной конфигурации. Оттуда они читаются, пока пользователь не сохранит настройки.

## Файлы

- `metadata.json`
- `extension.php`: хуки, обработка формы настроек, хранение конфигурации
- `configure.php`, `configure.phtml`: страница настроек
- `lib/DedupService.php`: логика поиска дублей
- `lib/DedupDAO.php`: запросы к базе
- `lib/TitleNormalizer.php`
- `lib/RuleRepository.php`: разбор и проверка правил
- `i18n/`: переводы
- `examples/sample-config.json`

## Риски

- Одинаковый заголовок не всегда означает одну и ту же новость, поэтому несвязанные статьи могут оказаться прочитанными
- Перепечатки с изменённым заголовком не распознаются
